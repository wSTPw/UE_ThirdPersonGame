## 一、项目一句话

在 UE 5.8 里复刻《怪物猎人：世界 冰原》的**普通雌火龙（em001/00）**，目标为**原作忠实**（决策、数值、时序、部位），首个验收配置为**下位单人**。项目自带严格证据分级制度：任何"忠实"主张必须能追溯到固定游戏版本（exe sha256 `c2ebbbd2…`）的原始资源、消费者代码或受控运行观测；社区资料只能当假设源，不能直接标"已证"。

## 二、当前进度（三条线并行）

### 线 1：资产与数值（基本完成）
- **848 条原作动画**已导入 UE 并逐条读回（19 个 LMT 容器/12 个有效 bank），旧 24 条时长已按源帧数修复。
- **模型**：雌火龙本体（142 骨含 Armature 根）+ 独立尾，4 材质（BML+NM+EM、damage），12 贴图；材质通道 RMT 实测接入。
- **数值 [已证+交叉]**：HP 基础 3000；12 组肉质（7 部位 + 5 个 MR 变体）；7 组硬直阈值（240/300/180/180/210/210/200）；发怒（累积 600/持续 80s/伤害 ×1.15/速度 ×1.05/玩家伤害 ×1.10）；疲劳（LR 70s/耐力 500–600）；异常全套（毒/眠/麻/气绝/疲劳/乘骑/爆破/捕获的 Base/Buildup/上限/持续）；陷阱（麻痹 8s/落穴 10s）；捕获阈值 30%。
- **公式化缺口**：任务倍率（每个任务对 HP/攻击/部位耐久的乘数）未落表——公开数据库（Kiranico）有逐任务表，可作为期望值回读验证。

### 线 2：行为与原作 AI 取证（进行中，最大缺口）
- THK（原作怪物 AI 思考表）**格式资格已通过 [已证]**：105 个 THK + 2 个 thklst，1795 节点/13015 指令段，字节重编码一致；损坏样本负例全部正确拒绝。
- **原生动作注册表已完整转储 [已证]**：344 条 `{动作名, 运行时ID, vtable}`（ID 10~212），布局 32 字节条目实证。关键发现：**ActionDumps 历史编号 ≠ 运行时命名空间**（同一运行时 ID 在不同分系统表中对应不同动作；如 BITE 历史 83→运行时 84，DASH_BITE2 86→87，ROLLING_TAIL_ATTACK2_L 75→101），THK emit id↔注册表 id 需逐动作核验。
- **条件语义（最大缺口，阻塞中）**：THK 段内 `functionType`（int32 @+8）共 60 种（全 13015 段使用），其中 32 个参数组合唯一。已实证解码式 `slot = packed & 0x1FF; bank = (packed >> 12) & 0xF`，但**每个条件函数"测什么"未闭合**。已穷举排除原生跳转表分发（4 种编码 + 2857 个 jmp-reg 站点），确认分发走运行时注册对象机制（name_lookup 为字符串注册表遍历器）。逐函数语义需 Ghidra 类型恢复或运行时观测。
- 首链抽样：咬击（BITE，注册表 84/历史 83）已全链打通到 UE：ACTP2 #15 → LMT bank2/slot1 → 动画 2.17s → COL uid32 攻击窗 0–0.383s（候选）。

### 线 3：UE 运行工程（B1 近似可玩）
- 首链执行框架（THK 执行器/源移动/源碰撞/Pawn，1546 行）+ **B1 近似 profile**（8 个新文件）：数据资产（数值按忠实度逐字段标注）、可替换决策接口（手写规则实现，未来换 THK 策略）、发怒状态组件、决策组件（动画资格门）、执行体（命中代理、运行时 Montage 混合、受击等级接入猎人原生受击表现链）。
- UE 5.8 构建通过。用户 PIE 反馈已收集 5 个问题（浮空/不移动/头不追视/攻击无衔接/受击无反馈），其中 4 个已有代码修复（修浮空的地面吸附、移动解阻、Montage 衔接、受击反馈接原生链），头部骨骼追视因骨骼命名未核对而暂缓。

## 五、已定的技术决策（供评审）

1. **双层产品线**：忠实线（证据闭合后逐条替换）+ 近似线（B1：真动画/真数值/手写决策，明确标 `approximated`，永不冒充原作）。B1 是脚手架，不是终点。
2. **工具路线**（2026-11-03 调研后）：
   - 文件解包：沿用 MHWNoChunk 原理的按需提取（已建 171,615 条索引），社区无质变替代品；
   - 数值层：公开数据库期望值 → 本机字节回读 → 双源一致才升 [交叉]（NUM-03 已按此闭合）；
   - 运行时层：MHW 属 MT Framework，选用 **LuaEngine（Gitee 社区注入器，轻量/内存读写/ImGui）** 替代自写 x64dbg 脚本，用于 BEH-01/EM_DMG/PBC 的运行时观测（需用户授权启动原作，第三方软件需自行评估风险）；
   - 静态层：Ghidra 类型恢复作为运行时样本的"解释器"（先采样后反编译，避免盲啃 84MB exe）。
3. **证据制度**：五级（官方机制/原始数据/消费者证据/运行验证/项目推断），任何代码行为改动都走变更记录（CHG），近似值必须显式标注，未证字段禁止默认填 0。

## 七、已知风险

1. **工作区未提交**：三大块新代码（首链/B1/Approx）+ 用户既有修改共处于未提交状态，误操作可能丢失。建议立即做 git 提交归档。
2. **B1 腐化风险**：近似层若持续自行加功能而不替换为证据闭合的实现，会偏离主线。需要"每闭合一条语义就替换一层规则"的纪律。
3. **第三方注入器信任**：LuaEngine 为社区软件，注入游戏进程有稳定性/安全风险；须快照游戏目录、不改安装、固定版本。
4. **构建环境问题**：本机 UBA（Unreal Build Accelerator）存储服务写损坏，构建需 `-NoUBA` 绕开（与项目代码无关）。
5. **单一 84MB exe 逆向成本**：Ghidra 自动分析耗时长；若描述符格式解析失败，运行时路线成为主路径（依赖用户配合）。

## 八、给评审者的具体问题

1. **BEH-01 路线取舍**：静态 Ghidra 类型恢复 vs 运行时观测（LuaEngine）——你会怎么排优先级？有没有第三条路（例如从社区已有的 THK 反编译产物反推条件命名）？
2. **证据标准是否过严/过松**：五级证据分级 + "社区数据只作假设源" 的做法，在个人复刻项目里是否值得？有没有更务实的平衡点？
3. **B1 脚手架的边界**：近似决策层应保持多"薄"才不算腐化？有没有更清晰的替换协议（接口/数据格式）？
4. **时间预估的合理性**：8–12 会话闭合核心忠实度（不含音画、不含全文对照）是否过于乐观？主要遗漏的风险点是什么？
5. **音画投入**：NBNK/EFX 解码 3–6 会话换"资源近似"级产出，在忠实度总目标里应排到什么优先级？
6. **是否有我们忽视的捷径**：以你对 MH 系列 mod 生态的了解，THK 条件语义/部位破坏耐久/受击选择这三类数据，社区是否已有我们没找到的公开解码成果？
